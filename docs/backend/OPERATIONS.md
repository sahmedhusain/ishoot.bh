# Backend operations

## Local stack

`docker-compose.yml` at the repository root. Everything binds to 127.0.0.1. Values come from `.env`; `./run.sh env sync` adds
the backend variables. Run `./run.sh env secrets` separately to generate missing secrets and service keys.

| Command                                        | Starts                                                           |
| ---------------------------------------------- | ---------------------------------------------------------------- |
| `docker compose up -d --build`                 | Postgres 17, Valkey, SeaweedFS, NATS, Mailpit, gateway, services |
| `docker compose --profile observability up -d` | OpenTelemetry Collector, Prometheus, Loki, Tempo, Alloy, Grafana |
| `docker compose --profile tools up -d`         | pgAdmin                                                          |

The compose Postgres uses the volume `pgdata17`, which is separate from the one older versions of this file created.
The Next.js apps use this Postgres through Prisma for unmigrated domains. Files use the Go service and S3.
See [DATA-MIGRATION](DATA-MIGRATION.md) before moving an existing installation.

## Database logins and pooling

Each service signs in as its own login, `svc_<service>`, which owns the service's schema and everything in it and
has no access to any other schema or to the apps' tables. `db-roles` (`backend/tools/db-roles`) makes the logins
before the migrations on every `docker compose up`, with the passwords from `.env` (`<SERVICE>_DB_PASSWORD`,
generated by `./run.sh env secrets`). It is idempotent: it rotates a changed password and hands the login any object
another login created in its schema, such as a table a Prisma migration moved there.

The services' request paths go through PgBouncer in transaction mode (`deploy/pgbouncer/pgbouncer.ini`):
`DATABASE_URL` points at it, and `DATABASE_DIRECT_URL` at Postgres for `migrate` and `worker`, which need a session
(locks, River). Behind the pooler a service's own `DATABASE_STATEMENT_TIMEOUT` cannot be kept per client, so the
login's default applies: `DB_ROLE_STATEMENT_TIMEOUT` (15 s), overridable per service with
`DB_ROLE_STATEMENT_TIMEOUT_<SERVICE>`.

After a Prisma migration that hands a table to a service, run `docker compose run --rm db-roles` (or restart the
stack) so the service's login owns it. Existing installs that ran everything as one login are converted the same
way on their first start.

## Events

A service writes each event to its own `outbox` table in the transaction that makes the change
(transactional outbox, `pkg/outbox`). Its relay publishes pending rows to the JetStream stream
`EVENTS` with the event ID as the message ID, so a re-sent event is stored once. When NATS is down, events wait in the
outbox and go out once it is back; nothing is lost. Watch `outbox_pending` and `outbox_publish_failures_total` on each
service's admin port, and the stream at `http://127.0.0.1:8222/jsz?streams=true`. Payload schemas are in
`contracts/events/`. Today the system service publishes its events and the audit service records every event (IT dashboard → Audit
trail); notify publishes the outcome of every message.

To read events locally: `docker run --rm --network platform_default natsio/nats-box nats -s nats://nats:4222 stream view EVENTS`.

## IT administrator recovery

First try an unused recovery code in the sign-in form's authenticator field. If none remain, an operator with
controlled access to identity's database login and MFA encryption keys can perform offline recovery. Record the
incident and operator ID before running this command; keep the terminal private, without output capture or session
recording, because it prints the new authenticator secret and recovery codes once.

```sh
docker compose run --rm identity recover-it -email it-admin@example.com -actor operator-123
```

The command prompts for the new password without echo (at least `IDENTITY_LOGIN_IT_PASSWORD_MIN_LENGTH` characters).
Piped input is supported, but do not put passwords in arguments or shell history. `-actor` is an operator ID, not a
name or email, of at most 191 letters/digits or `:._/-`. Recovery requires an existing **active** `it_admin` account;
it refuses missing, disabled, non-admin and other-realm accounts. It never creates, reactivates or promotes one.
The direct database URL is used, without the pooler.

The password, enrolled authenticator and recovery codes are replaced together, pending enrollment is cleared and
all account sessions are revoked. The account ID and role assignments are preserved. If any write, including the
audit outbox write, fails, the whole change rolls back. Do not retry after successful output: each successful run
replaces the just-issued credentials again. Enroll the new secret, store the recovery codes offline, then sign in
with the new password and authenticator. Verify that `identity.user.recovered` reaches the IT audit trail with
`changedBy=operator:<operator ID>`. If NATS is down, the event stays in `identity.outbox`; restore the relay and
verify delivery before closing the incident.

Rehearse only on a disposable stack, selecting it explicitly with
`docker compose -p platform-verify --env-file <disposable-env> run --rm identity recover-it ...`. Integration tests
exercise rollback on audit failure, revoked access/refresh sessions, invalid old credentials, replacement recovery
codes, preserved IDs/roles and refusal to reactivate or promote. This is an offline recovery procedure; IT account
management and staff/customer cutover remain separate migration work.

## Local mail and WhatsApp

The notify service sends every e-mail and WhatsApp message. Locally nothing leaves the machine:

- **Mailpit** receives every e-mail and shows it at http://localhost:8025 (API: `/api/v1/messages`).
- **The WhatsApp sandbox** (`backend/tools/whatsapp-sandbox`) answers like the WhatsApp Cloud API and lists what was
  sent at http://localhost:8095 (JSON: `/sandbox/messages?to=<number>`, `DELETE` to clear). Numbers ending in `0500`,
  `0429` and `0400` fail like a server error, a rate limit and a refused recipient; `POST /sandbox/fail` with
  `{"count": 3, "status": 503}` makes the next sends fail.

The IT dashboard's **Notifications** page shows each message's outcome and sends test messages. In production set
`NOTIFY_EMAIL_PROVIDER=integration` and `NOTIFY_WHATSAPP_CREDENTIALS=integration`, with the Resend and WhatsApp
integrations set up in the IT dashboard.

## Continuous integration

`.github/workflows/backend.yml` runs on changes to `backend/`, `contracts/`, `deploy/` or the compose file:

1. **Lint, scan and test:**
   - Generated code and docs must be current (`make gen-check`).
   - golangci-lint, govulncheck and gosec.
   - All tests with the race detector, with Postgres started by testcontainers.
2. **Images, one per service:**
   - Build, then a Trivy scan.
   - On `main`: push to GHCR with an SBOM and provenance, then sign with cosign.
3. **Helm:** `helm lint --strict` and kubeconform schema validation.
4. **Stack smoke test:** `docker compose up --wait`, then probe the gateway.

`.github/workflows/ci.yml` (the Next.js apps) also runs `tests/unit/catalog-sync.test.ts`. That test keeps
`contracts/catalog` equal to the TypeScript constants; `npm run catalog:sync` rewrites the catalogue after a constant
changes.

## Kubernetes

Chart: `deploy/helm/platform`. There is one entry per service under `services:`.

- **Per service,** the chart creates:
  - a Deployment with probes on the admin port and a hardened security context;
  - a Service and a PodDisruptionBudget;
  - an HPA, a ServiceMonitor and a NetworkPolicy;
  - a ConfigMap for mounted files.
- **Ingress:** the gateway is the only service behind the Ingress, with TLS from cert-manager.
- **Secrets:** shared secret values (for example `REDIS_URL`) come from the `platform-shared` Secret, and each service
  can also have `<service>-secrets` (its `DATABASE_URL` through the pooler and `DATABASE_DIRECT_URL`, both as its own
  login). Both are created by External Secrets, never by the chart.
- **Database logins:** the `db-roles` hook Job runs before the migration Jobs with `db-roles-secrets` (the database
  owner's `DATABASE_URL` and `DB_ROLE_PASSWORD_<SERVICE>`).
- **Per environment:** overrides live in `values-staging.yaml` and `values-production.yaml`.

### Deploy

1. Merge to `main`. The Backend workflow builds, scans, signs and pushes images tagged with the commit SHA.
2. Run the **Deploy** workflow with the environment and that SHA. It verifies the image signatures, then runs
   `helm upgrade --install --atomic`. Production waits for the GitHub environment approval.

The cluster needs ingress-nginx, cert-manager, the Prometheus Operator, External Secrets and a NetworkPolicy-capable
CNI. Postgres in Kubernetes is planned through CloudNativePG, with its built-in PgBouncer pooler and backups to
object storage.
