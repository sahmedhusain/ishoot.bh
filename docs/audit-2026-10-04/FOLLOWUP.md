## Deployment requirements

1. Inspect target schema drift before applying the completion migration, particularly on a database previously updated using `db:push`. Back up and verify restore first. Only disposable local databases have been migrated here.
2. Coordinate the token-hashing migration with the new application version. The previous application expects raw tokens and cannot read hashed rows. During cutover, prevent the old version from creating raw session rows after migration. Existing JWT cookies remain valid with the new version after hashing. Application rollback needs an explicit session-invalidation/re-login plan; hashes cannot be reversed.
3. Require `JWT_SECRET` of at least 32 UTF-8 bytes. Preserve the actual signing secret during session-storage migration; changing it invalidates existing JWT cookies.
4. Deploy the revalidation worker with the same database, `WEB_URL` and `REVALIDATION_SECRET` as the apps: `pnpm worker:revalidation`. `pnpm worker:revalidation -- --once` is a finite operational check. No production worker was started here. Monitor pending/failed jobs and worker uptime; restart safely after crashes. Failed jobs after eight attempts require an operator-reviewed retry. A separate email worker is now implemented; production sender verification and delivery evidence remain.
5. Invalidation tags are app-local. A multi-instance/self-hosted deployment needs a shared Next.js cache/invalidation arrangement or per-instance delivery; this local single-instance test does not prove distributed cache coherence.
