# Platform audit and optimization — 4 October 2026

**Current implementation status:** read [FOLLOWUP.md](FOLLOWUP.md). This report preserves the original audit baseline; the follow-up supersedes findings and validation outcomes that have since changed.

Both applications build, the isolated database migration history now matches the Prisma schema, and the critical permission, calendar privacy, meeting signature, and financial query problems described below have fixes in this working tree. The platform still needs the follow-up work in the open findings table before claiming full production performance or complete workflow correctness.

## Scope and evidence

Reviewed the shared database layer, both Next.js applications, middleware, API handlers, server actions, CRM/request workflows, finance calculations, company/CMS configuration, permissions, uploads, deployment configuration and build outputs. The generated [source inventory](INVENTORY.md) covers **283 source files, 12 API handler functions, 85 exported server actions and 37 Prisma models**. It identifies **60 `findMany` calls, 49 without an explicit `take`**. This is a syntactic inventory: small configuration collections may legitimately be unbounded, and it does not mean every action or UI interaction was executed.

Changes and testing used a disposable PostgreSQL 15 container, synthetic accounts and records, and dedicated local production-build servers. No production database, deployment, real customer correspondence or existing local servers were changed. Email delivery was disabled during HTTP checks. This audit does not establish production latency, connection capacity, backup recovery, hosting configuration or absence of all possible bugs.

The explicitly requested graphify and engineering system-design skills were used. Existing graph: **1,671 nodes / 3,728 links**, built at commit `8ce4dc27ac1508e56e59b6495c7b91156fc8db14`. The graph predates this working tree and was used for navigation, with findings independently checked against source and tests. Query budget: **3,500 tokens**, 442 candidate nodes / 95 shown; no extraction model was run in this audit, so new extraction token cost is **0**. Total audit model token usage is not available here. Graph completeness/cohesion was not recalculated; no raw cohesion score is claimed. The graph was not rebuilt and must not be treated as a complete current dependency map.

## Measured financial query improvement

Fixture: 1,004 invoices, 1,003 payments, 1,002 expenses and 2,000 line items, including correctness edge cases. Compared summary plus six-month cashflow against pre-audit finance source at `447326d282b186d7adc12cf7f0bfea5ed6e96c7c`. Five warm runs after `ANALYZE`, same local disposable database:

| Measurement                     |            Previous implementation |        Current implementation |
| ------------------------------- | ---------------------------------: | ----------------------------: |
| Median elapsed time             |                           90.18 ms |                       6.20 ms |
| Samples, ms                     | 95.70, 90.18, 87.04, 86.94, 183.97 | 6.20, 6.74, 3.64, 5.06, 10.05 |
| ORM read operations             |                                  5 |                             2 |
| Materialized source-record JSON |                    3,282,008 bytes |         0 source-record bytes |
| Final summary + series JSON     |                          477 bytes |                     477 bytes |

Approximately 93% lower median in this fixture. “0 source-record bytes” means full mapped records are no longer fetched; aggregate database results still have wire overhead. ORM operations are not a count of all underlying SQL statements. This is not an HTTP payload, whole-page TTFB or production load benchmark. Query planning/statistics materially affected earlier runs; stale-statistics runs did not consistently improve. Maintain autovacuum/analyze and validate against production-shaped data. Recorded `EXPLAIN ANALYZE` execution times were 1.986 ms for summary and 1.762 ms for monthly aggregation.

Financial parity checks cover BHD versus other currencies, void/draft treatment, partial paid VAT, overdue Bahrain calendar dates, zero-filled months, category totals and period bounds. This preserves the established **BHD-only** financial-summary semantics; it does not introduce FX conversion or change accounting policy.

## Strengths retained

- Shared Prisma/database package gives both apps one data model and avoids an unnecessary internal HTTP hop for server-side reads.
- Server authorization checks use live session/user records, so account revocation and role changes need not wait for JWT expiry. Middleware alone is not trusted for database permission decisions.
- Existing invoice writes include transactional line items and financial snapshots; payment create/edit has ledger reconciliation safeguards. New deletion locking aligns with those safeguards.
- Public inquiry/review paths already have idempotency, moderation, separate complaint behavior and recorded email delivery state. Regression tests retained these behaviors.
- Published website snapshots separate draft editing from live content. This is a useful foundation for a reliable cache and publish pipeline.
- Shared bilingual types/translations and reusable UI/PDF components support consistent CRM presentation, provided status and accounting definitions are made explicit.

## Release plan

1. Review source changes and open P1 findings. Back up the target database and verify restoration; record schema/migration history and reconcile drift before migration.
2. Set strong environment secrets and Docker credentials. Run normal production build with actual deployment environment. `.next-audit` is only the local verification build directory.
3. On a reconciled target, deploy migrations through `prisma migrate deploy`; use `pnpm db:bootstrap` only when initial settings/accounts/grants must be provisioned. It preserves existing rows and passwords, but fills missing grant rows from bootstrap policy. Review that policy first. Never use demo `db:seed` in production.
4. Test missing/custom/denied/export permissions, super administrator access, company identity/artwork, calendar privacy, concurrent ledger changes and meeting approvals in staging. Verify publish/revalidation, upload persistence and actual email delivery separately.
5. Observe errors, query volume, payloads and p95 latency after canary release. Plan rollback of application code without dropping financial/CRM data. Reverting to old permission code reintroduces fallback grants, so prefer a forward fix for auth defects. Schema rollback requires an explicit data-preserving plan.

The current working tree is a verified first optimization and security pass plus a full scoped source audit, not a certification that every open finding is resolved. Nothing has been deployed to production.

Additional delivery clarification: `components/shared/DeliveryToolbar.tsx` still imports seed company identity for mail-client subjects and marks email as sent after opening `mailto:`. Opening a compose window does not prove delivery. Pass the stored company name explicitly and show a compose/opened state; reserve sent for confirmed provider delivery. PDF/download UI export-grant behavior should also be reconciled with the server endpoint's read-grant policy.
